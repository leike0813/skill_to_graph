# 检索证据并写报告

围绕一个问题，从本地证据目录中自主检索、判断证据是否充分，形成报告提案，经用户确认后写入 `report.md`。
检索阶段的判断由你按语义做出；流程按固定次序推进：校验输入、检索与判断、确认、写入。

## 输入

- `question`：要回答的问题，非空。
- `catalog`：证据目录文件的路径，UTF-8 编码的 JSON 对象，键为证据标识，值为证据文本。
- `output_dir`：报告的输出目录路径。

`question` 和 `catalog` 由调用方在首次调用时提供，`output_dir` 在写入前确定。含义不清时先问清楚，不要猜。

## 步骤

### 1. 校验输入

在检索前检查：

- `question` 非空，去掉首尾空白后仍有内容；
- `catalog` 文件存在、可读、是 UTF-8 编码，能解析为 JSON 对象，值都是字符串。

任一条不满足就停止，不调用 `lookup`，不写任何文件，返回结构化错误，说明失败条件与位置。

### 2. 检索并判断证据充分性

你自主决定查哪些证据、查几次。每次检索只能用 `lookup(key)` 工具读取 catalog 中某个键对应的证据文本；
不要用其它方式绕过 `lookup` 直接读取 catalog 文件，也不要引入外部搜索或网络检索。

拿到证据后自己判断：这些证据是否足以回答 `question`。

- 足以回答：停止检索，整理报告提案。
- 不足以回答：继续选下一个键调用 `lookup`，直到证据足够。
- catalog 中不存在能支持答案的证据：停止检索，返回 `insufficient`，不写任何文件。

停止条件是语义上的证据充分或证据不可得，不是检索次数，也不是报告长度或字数。
证据充分与否由你判断，流程不替你数检索轮次。

`lookup` 调用故障时停止，返回 `failed` 并带上错误信息，不重试、不换路径重试。

### 3. 报告提案与确认

证据足够时，生成报告提案：内容直接回答 `question`，每一处结论都标注所依据的证据键。
把提案内容、所用证据键和将写入的路径说清楚，向用户提出一个明确的二选一确认问题：请用户回复 `true` 批准写入，或回复 `false` 放弃。

在收到用户回复之前，不要创建输出目录，不要写任何业务文件。

### 4. 按回复处理

- 回复不是 `true`（包括 `false`、空回复、其他内容）：返回 `cancelled`，不写任何文件。
- 回复是 `true`：
  - 目标文件是 `<output_dir>/report.md`；
  - `output_dir` 不存在就创建它；
  - 目标文件已存在就失败，不覆盖已有内容，返回结构化错误并说明该路径；
  - 写入的内容是第 3 步的提案，不自己另写一份。

文件写入出错时停止，不重试、不换路径重试。已写出的部分内容按实际发生报告，不当作成功。

## 输出

检索阶段的模型输出固定为三个字段，供流程节点读取：

- `status`：`sufficient` 或 `insufficient`
- `report`：报告提案文本，证据不足时为空
- `used_keys`：实际查过并被引用的证据键列表

流程的业务结果：

- `status`：`ok`、`cancelled`、`insufficient`、`failed` 或 `error`
- `report`：报告提案文本，仅在适用时给出
- `path`：实际写入的文件路径，仅在写入成功时给出
- `used_keys`：被引用的证据键列表
- `error`：结构化错误，含错误码、位置和原因，无错误时不出现

各状态的含义：

- `ok`：已确认并写出 `report.md`
- `cancelled`：用户未确认，未写文件
- `insufficient`：catalog 中没有能支持答案的证据，未写文件
- `failed`：`lookup` 工具调用故障，未写文件
- `error`：输入校验失败，未写文件

不要用状态字符串代替实际文件，文件是否真的存在由写入方确认。

## 运行前提

`lookup(key)` 是运行环境提供的本地文件工具，读取 `catalog` 指定的文件并返回该键的证据文本；它不需要网络访问。
本流程需要模型来做键的选择和充分性判断，判定结果由模型给出并按上面的字段返回。
